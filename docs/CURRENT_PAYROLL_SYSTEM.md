# 当前工资核算系统说明书

## 说明范围

本文档还原截至 2026-09-08 已存在的工资核对流程。依据是当前工资 Skill、Skill 内脚本、2026 年 8 月实际目录、7 月工作总结、1 月 legacy 项目和 8 月最终工作簿的结构检查。

本文档不是未来架构设计，也不把旧版本合并成一个“正确版本”。当 Skill、Python 和实际文件之间有差异时，本文档保留差异并标为待确认。

## 1. 系统解决的问题

当前系统要把排课系统的实际上课记录，转换成教师工资表中的一对一、班课、课时单价和总课时费核对基线，再把教师填报、续费推荐、退费、兼职和管理岗位绩效等不能完全由排课记录推出的项目汇入最终薪资表。

核心中间产物是“工资核对表”，而不是最终薪资表。它至少包含：

- `排课记录`：经筛选、年级/学科/班型归一和系数公式处理的逐课记录；8 月最终版本还增加了 `上课学员`、`上课时间` 两列用于追溯。
- `工资核对`：按教师汇总一对一系统值、教师填报值、差值，以及班课系统值、教师填报值、差值。
- `填报数据`：8 月实际最终工作簿中为隐藏页，用 VLOOKUP 连接当月合并薪资表的 AA/AC；这是工作簿实现，不是独立 Python 程序。

## 2. 8 月实际输入

8 月实际目录中可以确认的输入类别如下。原文件留在本机，未复制进仓库：

| 输入 | 8 月实际文件类别 | 在流程中的作用 |
|---|---|---|
| 排课源 | 两个不同日期导出的排课列表 | 生成逐课核对底稿；中段导出版被作为年级权威基准，最终表保留学员和时间追溯列 |
| 数学填报表 | 8 月数学薪资表 | 提供数学教师 AA/AC、星级、批注及工资表其他人工填报字段 |
| 理化填报表 | 8 月理化薪资表 | 提供理化教师 AA/AC、星级、批注及工资表其他人工填报字段 |
| 续费/推荐表 | 续费+推荐年度工作簿的 `8月` 页 | 提供 AH/AI/AJ；AK 按表内公式计算并与源表总计交叉核对 |
| 退费表 | 退费统计表的 `8月份` 页 | 按扣款教师列归属，取人头和业绩形成 AN，并写批注 |
| 组数据统计表 | 数学、理化统计工作簿的 `组课时生产`、`学生` 等页 | 支持生产课时、平均课次和管理岗位绩效；部分总学员数仍人工读取 |
| 管理考核表 | 8 月管理/学科组考核工作簿 | 保存管理或学科组考核结果；并非工资核对底稿的自动输出 |
| 参考文件 | 5 月/6 月工资表、规则文档和上月备份 | 作为星级或人工特殊值的参考，不是每次都由脚本自动读取 |

实际工作目录还包括多个“改某项前”“公式版”“数值版”“跨文件版”“加溯源列前”等备份。这些备份证明流程是多轮迭代的，但不能单凭文件名判定哪一版最终正确。

## 3. 当前实际流程

### 3.1 先形成核对底稿

1. 人工准备当月排课导出、两张学科填报表、续费/推荐表、退费表和必要的统计表。
2. 以排课列表为系统基线。`build_8月核对表.py` 是 8 月最初的生成程序；通用版是 Skill 中的 `import_paikeshi.py`。
3. 读取排课行，保留 `上课状态=已上课` 且 `实到>0` 的记录；旧版脚本兼容 `实到人数`，新 8 月脚本使用 `实到`。
4. 每条保留记录写入 `排课记录`：老师、年级、学科、班型、实到人数，以及 F/G/H 三个班课绩效/年级系数/人数系数公式。当前 Skill 另外要求保留学员和时间两列用于溯源。
5. 班型统一为 `1对1`、`小班`、`1对2` 等；年级从班级名、衔接班映射、领航规则或脱敏查表提取。8 月实际先经历过“一刀切回调一级”的脚本版本，之后以中段导出版人工纠正并形成最终表，不能把最初脚本输出当成最终口径。
6. 按排课记录中出现的教师形成 `工资核对` 教师名单。工资核对表在实际流程中是进入最终薪资表的名单闸门，但全职无课、兼职无课和跨组人员仍需要人工确认。

### 3.2 计算系统基线并与填报对照

7. `工资核对` 的 D–O 按年级汇总一对一排课记录；每个年级的小时折算乘以 3。Q 汇总不同年级的折算小时。
8. T 用排课记录的班课绩效汇总并乘以 2，作为班课系统值。
9. R/U 读取教师填报的 AA/AC；S=`Q-R`，V=`T-U`。最终 8 月工作簿中的 R/U 通过 `工资核对 → 填报数据 → 当月合并薪资表` 的 VLOOKUP 链路读取。
10. 用户先检查 S、V 全表非零项，再用逐课的学员和时间追踪差额。重点包括：实到为 0 但状态为已上课、漏填课次、错行、代课折算和班课批注与系统不一致。
11. 批注不是装饰：AC 班课明细、I/J 一对一信息、AN 退费明细都要与来源比对。当前 Skill 要求只在确认后改填报值；如果只是批注错误，可以只重写批注并保留数值。

### 3.3 处理课时费、续费、退费和兼职

12. 用 `verify_ae_af.py` 报告 AE/AF 与 AD、星级、TRMT 规则不一致的行。它只读并报告，不改原表。星级不可信时，使用人工确认或覆盖表；管理/底薪行可跳过。
13. 续费解析由 8 月 `parse_续费校对.py` 和后续 `parse_续费校对_v3.py` 完成。两个脚本读取本机消息导出和名单 JSON，输出解析结果 JSON；它们不直接写工资表。v3 增加了“第一名字判断校区”、别名/错字映射，并将任课老师之间的课时按人数分摊。
14. 续费源表的 1V1、班课、领航合计分别进入 AH、AI、AJ；AK 使用 `AH*1 + AI*1.5 + AJ*0.75` 公式，并与续费源表总计交叉核对。实际 8 月仍有人工确认与版本比对。
15. 退费按退费表的扣款教师列归属，不按学科教师列猜。人头和业绩两种负数口径相加写入 AN，并留下退费明细批注；月份缺失、扣款对象不明确、历史政策区间等必须人工裁决。
16. 兼职不走 AA/AC 折算体系，按当月确认的节数和单价计算 AF，写静态值并留批注。单价不是由脚本稳定推导的月度常量。
17. 管理岗位绩效通过管理考核规则和组课时生产、续费、退费等数据计算或人工汇总到 AM。`compute_kh_metrics.py` 能读取部分指标，但总学员数等项目仍打印给人取数，且不写工资表。

### 3.4 合并并完成最终薪资表

18. 人工将数学、理化填报表按当月名单合并为总薪资表，保留批注、公式和人工修正；7 月备份链明确显示了续推、退费、管理绩效、星级、人事字段等分阶段填写。
19. 在最终表中检查 AD/AE/AF、AH–AK、AM、AN、AV，以及兼职行、管理行、教师名单和批注。
20. 当前 Skill 的最终检查顺序是：S/V 差值全扫 → 差额溯源 → AE → AF/AV → 年级 → 续费/退费/兼职 → 名单和管理行。这个顺序是 Skill 规则，不是单一程序的流水线。

## 5. 各层分别做什么

### Skill

Skill 是操作规程、业务口径、字段映射、人工确认清单和异常处理说明。它规定输入材料、公式、批注格式、年级规则、版本选择、备份要求和 2026-09-08 的全量复查顺序。它不是一个自动调度器，也不会自动保证每项检查都执行。

### Python

Python 目前承担四类工作：排课源读取和底稿生成；年级/学科/班型提取；AE/AF 只读验证；8 月续费消息解析和管理考核部分指标读取。若输入不符合预期，程序会失败、跳过或输出待处理项，后续仍依赖人工。

### Excel/WPS/业务系统

Excel 公式实际承担汇总、差值、AK 奖励、工资总额和跨表引用。排课系统提供原始课次、状态、实到、班型、班级名、学员和时间。续费/退费表自身的字段和公式也是业务口径来源。桌面版打开核对表时是否更新外部链接，会影响 R/U 是否得到最新填报值。

### 人工

人工决定版本权威、特殊年级、代课折算次数、星级覆盖、兼职单价、退费归属和月份、续费版本冲突、管理岗位取数、差额是否接受，以及最终是否进入薪资表。人工还要确认自动程序输出的未知年级、解析失败和名单差集。

## 6. 2026-09-08 漏洞与全盘复查

### 原来为什么会漏

8 月实际的早期核对动作曾主要盯着班课 V 列和班课批注。工资表自身的公式可以正常计算，V 列也可能没有明显异常，因此“表内公式没坏”并不等于“填报值与排课源一致”。一对一差额在 S 列；如果没有同步扫 S，且没有用排课源的学员/时间重新对照，就不会进入人工清单。8 月最终核对表此前没有 I/J 溯源列时，即使发现差额也难以定位到哪一节课。

这是已被当前 Skill 明确记录的历史教训：一对一差值曾被漏检，后来才发现存在明显差额。这里的漏洞不是某个公式算错，而是检查覆盖面和溯源链不完整。

### 现在新增了什么

当前 `SKILL.md` 2026-09-08 17:28 修改版新增/强化了：

- S（一对一差值）和 V（班课差值）都必须全表扫非零；
- 差值必须回到逐课排课记录，使用 `上课学员`、`上课时间` 溯源；
- 检查实到为 0、漏节、错行、代课折算和 N–Z 填错行；
- 继续检查 AE、AF/AV、年级、续费/退费/兼职和名单；
- 每项输出“全对”或异常名单，完成一项后再进入下一项。

当前 8 月最终工作簿也确实有 10 列排课记录，包含 `上课学员`、`上课时间`；这为人工溯源提供了数据基础。

### 是否有程序保障

没有完整的程序强制保障。现有 Python：

- `import_paikeshi.py` 和 8 月生成脚本能写排课底稿和部分公式；
- `verify_ae_af.py` 只验证 AE/AF；
- 续费脚本只输出解析结果；
- 管理脚本只读取/打印部分指标。

没有一个现存入口会自动完成“扫 S/V → 逐课溯源 → 续退兼职 → 名单 → 管理行 → 输出通过/异常”的全链路。因此全盘复查目前是 Skill + Excel + 人工执行要求，尚未成为 Python 强制门禁，也没有在仓库中看到对应测试。

## 7. 当前已知风险

1. 最终工作簿依赖外部 VLOOKUP 链路；路径、文件同时打开和 WPS/Excel 更新链接行为会影响填报值。
2. 年级规则存在脚本版本和实际最终口径的历史差异；8 月早期脚本与中段导出版权威定级并不相同。
3. 续费消息解析依赖名单、别名、校区首名和自然语言格式；解析失败、外校单和多人分摊需要人工复核。
4. 退费、代课、兼职、星级、管理绩效存在人工裁决；其结果可能只存在于批注、聊天或某个备份版本。
5. 全盘复查没有单独的自动门禁，且历史流程中过度关注班课会漏掉一对一差额。

## 8. 尚未搞清的问题

- 8 月最终工作簿的每一次人工改动，无法仅凭文件名完整还原责任人和确认时点。
- `build_8月核对表.py` 是生成起点，但不能证明它是最终交付入口；最终版包含其后人工和工作簿层面的改动。
- `parse_续费校对.py` 与 `_v3.py` 的正式采用边界没有单独的运行日志；v3 从代码看是“最终口径”，但实际提交到薪资表仍需人工。
- Skill、8 月实际脚本和最终 Excel 之间没有统一的运行记录或版本绑定。
- 管理岗位考核的完整业务标准仍有部分只存在于表格/自然语言，`compute_kh_metrics.py` 不是全量计算器。
