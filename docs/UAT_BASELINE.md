# UAT Baseline

> 目的：把真实用户已经发现、确认过的问题和产品行为固化到仓库中，
> 作为后续 Ralph / Worker / Chief / Machine Gate 的长期验收基线。
>
> 本文件不保存真实工资、学生、教师薪酬等敏感数据。

## 1. 核心原则

- 真实 UAT 优先于继续扩功能。
- 当前第一目标始终是：
  真实课表 → 正确工资 → 可核验 Excel。
- 用户发现过一次且可以自动化的问题，应尽量转成永久 regression test。
- 问题优先级：
  BLOCKER / WRONG_RESULT > UX > LATER。

## 2. 核算月份

### 默认月份

- 每月 20 日之前：默认上一个自然月。
- 每月 20 日及以后：默认当前月。
- 用户始终可以手工切换。

例如：
2026-09-12 打开工资核算，
默认应为 2026-08。

### 上传课表月份核对

用户当前选择的月份不能成为机械阻断条件。

上传课表后，应根据实际上课日期判断课表主要属于哪个月份。

例如：

当前 UI = 2026-09
上传课表主要属于 = 2026-08

系统不应直接拒绝。

应该提示：

“检测到该课表主要属于 2026-08，
当前核算月份为 2026-09。
是否切换至 2026-08？”

操作：

- 切换到 8 月
- 仍按 9 月

不能静默修改月份。

### 人工月份 / 权威月份

如果存在人工月份表、权威月份资料或已确认月份规则，
必须与课表实际日期交叉核对。

不能只相信文件名。

需要结合：

- 实际上课日期
- 人工月份 / 权威月份
- 文件名
- 业务周期完整性

如果一个“8月课表”实际日期明显缺失、跨月或异常，
不能静默计算，应提示。

## 3. 基础资料

新建工资核算时，应自动加载已有权威资料：

- 历史年级证据
- 系统权威星级
- 上传资料星级
- 人员规则
- 已确认个人政策
- 工资模板

不能只有测试代码手工灌数据库以后才得到正确工资。

## 4. 工资核心链

必须持续守住：

原始课表
→ 年级
→ AA
→ AC
→ AD
→ 星级
→ AE
→ AF
→ 后续项目
→ 最终工资

已确认正确的数据不得因为后续开发静默回归。

课时=0 / 无有效上课事实的记录不得参与工资核算。

AD = AA + AC。

## 5. 星级

优先级固定：

1. 系统权威星级
2. 上传资料星级
3. 两者都没有 → 默认二星

发生冲突：

- 系统权威优先
- 保留冲突记录
- 不阻塞工资生成

## 6. 无发生项目

当月确实没有发生：

NO_EVENT → 0

理论上应有数据但来源没有加载：

MISSING_SOURCE

不能把 MISSING_SOURCE 伪装成 0。

## 7. Golden Baseline

Golden Baseline 是开发答案册，不是生产输入。

必须：

- 只读
- 不得为了让测试通过修改 Golden
- 不得直接抄教师最终工资结果
- 可以恢复标准公式结构和模板结构
- 持续检查 Golden Value Diff
- 持续检查 Golden Formula Diff

已确认 MATCH 的字段不能静默变化。

## 8. Excel

最终 Excel 应保持真实工资模板结构。

当前明确需要公式的项目：

- 一对一相关折算
- 总课时费
- 最终收课小时
- 后续折算课时

班课课时允许直接写值。

禁止用：

=68.77

这种伪公式冒充真实业务公式。

输出后必须重新打开并验证公式仍然存在。

## 9. 导出

普通用户不填写文件路径。

默认导出到用户可以找到的位置，例如：

Desktop/工资导出

同名时：

工资表.xlsx
工资表 (2).xlsx
工资表 (3).xlsx

不得：

- 静默覆盖
- 因文件已存在直接失败

如果 fallback 到其他位置，
UI 必须明确告诉用户文件在哪里，
最好支持“打开所在文件夹”。

## 10. 文件恢复

所有上传文件必须支持：

- 查看
- 替换
- 删除
- 重选
- 重置
- 返回

选错文件一次不能让整个流程死掉。

## 11. 错误提示

普通用户 UI 禁止直接显示：

missing normalized schedule columns

此类工程信息。

应该显示人话，例如：

《8月排课表.xlsx》无法作为排课表使用。

缺少：
- 任课老师
- 上课时间
- 教学形式

请重新选择正确文件。

## 12. 真实文件

不能只靠 synthetic fixture 宣称完成。

长期回归要覆盖：

- Excel
- WPS
- 公式
- cached value
- 合并单元格
- 旧模板
- 缺列
- 错文件
- 重复上传
- 文件替换

## 13. UI 主流程

主流程固定倾向于：

数据准备
→ 自动核算
→ 异常核对
→ 工资预览
→ 导出工资表

普通用户不需要理解：

- Run
- Adapter
- YAML
- 数据库
- 内部路径
- Excel 字母字段

## 14. 范围

### 2026-07 规则重建

- July 的真实工资表、核对表、排课源和模板结构已登记为本机只读证据，规则快照见 [`JULY_2026_RULE_RECONSTRUCTION.md`](JULY_2026_RULE_RECONSTRUCTION.md)。
- July 与 August 使用不同的日期化 Core 版本；Run 级人工确认不会跨月份继承。
- AA、AC、AD、AE、AF 的历史差异按字段分类并保留来源证据；差异没有依据时继续显示待确认。

工资主流程没有稳定以前，不要自行扩成：

- 完整续费系统
- 完整退费审批
- CRM
- HR
- BI 大屏
- AI 聊天
- 教师评分系统

## 15. UAT 节奏

推荐长期工作方式：

用户真实使用
→ 产生真实问题
→ 整理 UAT backlog
→ Ralph / Worker 施工
→ Machine Gate + Golden Gate + Chief
→ 用户测试新 checkpoint

用户负责体验和判断，
不要求用户自己写工程测试报告。

## 16. 用户动作与后台审计

后台 audit evidence 与用户待办不是同一个数量。

- 多条字段级记录如果来自同一个根因，应聚合为一个清晰的用户动作。
- 普通正常情况由系统按已确认规则处理，不得为每位教师重复制造确认项。
- 顶层待办数量应尽量接近用户实际需要完成的动作数量；明细证据可以保留在审计层。
- “来源不是最高权威”不自动等于错误或阻塞；必须根据业务规则标记为信息、核查动作或真正阻塞。

## 17. 星级与义务课时的动作语义

星级按以下规则处理：

1. 系统权威星级优先。
2. 无系统权威值时使用上传资料/提交工资表中的星级。
3. 两者都没有时按已确认规则默认二星。
4. 权威值与上传值冲突时采用权威值，同时保留双方来源和冲突证据。

上述情况均是确定性结果，不应按教师逐行生成“需确认”问题。若本月没有完整权威星级资料，用户层应聚合为一个“核查本月星级资料”动作，明细中展示各人的来源、fallback 或冲突情况。

AF 的常规政策应由系统按既定规则执行。只有检测到免扣义务课时、TRMT/管理或其他明确的个人特殊政策时，才产生针对少数例外的一次性确认动作；没有例外时也只能提供统一的“确认无人免扣/添加特殊人员”检查，不得为普通教师逐人制造重复待办。不得因此改变已确认的 AF 公式。

## 18. 差异与严重级别

- expected 与 actual 相同，或在规定容差内 difference = 0，必须标记为 `MATCH`/已核对，不得进入待处理或人工确认。
- 红色仅用于阻塞工资生成、结果明显不可信或必须处理的问题。
- 黄色用于建议核查、fallback、来源等级或少量政策例外。
- 绿色用于已确定、已核对和 MATCH。
- 灰色用于信息、不适用和仅供审计的记录。

底层有 evidence 不等于存在红色错误。字段检查、业务分组和用户 Action 聚合都必须保留差异为零的 MATCH 语义。

## 19. 操作反馈与主导航

上传、导入、读取资料包、核算、重新核算、生成和导出等耗时操作必须：

- 点击后立即进入 disabled/loading 状态并显示当前阶段；
- 禁止重复点击；
- 成功后恢复可操作状态并显示结果；
- 失败后恢复可操作状态，给出中文说明和可追查的错误编号；
- 只显示真实阶段（资料读取、数据识别、工资计算、文件生成），不得伪造无来源的百分比。

顶部导航应服务于“数据准备 → 自动核算 → 核对/检查 → 工资预览 → 导出工资表”这一主流程，避免拥挤、重复或直接暴露内部模块。历史入口在历史系统完成轻量索引前可以暂时隐藏；不得因此删除历史数据或让首页加载全部历史 Run。

## 20. 学科组资料与文件流程

学科组资料应支持一张统一资料卡，并允许用户追加多份文件（例如数学组、理化组）。系统应根据文件内容识别教师、学科、Sheet 和来源；普通用户不需要理解内部 adapter role、`math`、`science` 或 `SCOPE_ROLE`。文件流程必须有明确成功/失败反馈，支持查看、替换、删除、重选和重置，且不能因为一次选错文件导致流程失效。

## 21. 错误边界与历史范围

Unexpected server errors 必须在 HTTP 边界内返回可理解的中文错误和 error id，服务保持存活，完整 traceback 只写技术日志；不得把 `Failed to fetch` 或 traceback 直接交给普通用户。若旧失败的底层根因没有历史证据，应如实标记为 UNKNOWN，不得把“异常越过 HTTP 边界”冒充底层 root cause。

续费、退费等外围能力在工资主链稳定前暂缓扩展；本基线只要求已接入的数据可追溯，不要求借此开发完整管理系统。

## 22. 回归硬规则

后续每轮能够自动化的真人 UAT 问题都应转成 regression，至少持续守住：

- 差异为零不产生用户确认动作；
- 星级 fallback、默认二星和权威冲突不产生逐教师人工问题；
- AF 普通政策不产生逐教师重复 Action，少数例外仍可核查；
- 同一根因可聚合为一个或少数用户动作；
- 耗时按钮可 loading、禁重复点击并在失败后恢复；
- unexpected server error 返回中文 JSON 且服务存活；
- 首页不主动加载或渲染全部历史；
- Golden Value Diff 与 Golden Formula Diff 持续为 `NONE`。

总原则：系统处理多数正常情况，人只处理少数真正例外。
